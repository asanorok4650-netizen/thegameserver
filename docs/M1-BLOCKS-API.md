# M1: ブロック・ゲームAPI拡張仕様

対象ブランチ: `milestone/m1-core-blocks-api`

## 目的

Blocklyで構築できるゲームロジックを拡張し、ブロックとゲームエンジンの間に安定したAPI境界を設ける。自然災害サバイバル専用の実装ではなく、複数ジャンルで再利用できるCore機能として整備する。

## 現状

- Blocklyワークスペースは `src/studio/BlocklyEditor.jsx`。
- Blockly JSONからデータ専用IRへの変換は `src/scripting/compiler.js`。
- 旧eventRulesとBlockly IRの統合は `src/scripting/ir.js`。
- IRの実行は `src/scripting/runtime.js`。
- エンジンとの接続は `src/game/engine.js` の `_createUnifiedRuntime()`。
- Runtimeは任意JavaScriptを評価せず、命令実行量・タスク数・反復数に上限を設ける。
- 現状のBlocklyツールボックスには、Runtimeで未対応の標準ブロック（例: `controls_whileUntil`）が含まれる。M1では「表示されるブロックはコンパイル・実行できる」状態を完了条件にする。

## API設計原則

1. **データ専用IR**: Blocklyは直接JavaScriptを生成・実行しない。新機能はIR命令として表現する。
2. **名前空間**: APIは `world`、`player`、`part`、`game`、`time` 等の領域に分け、エンジン内部オブジェクトをRuntimeへ露出しない。
3. **アダプター境界**: Runtimeは抽象APIのみを呼び、Three.jsやGameクラスの内部構造を知らない。
4. **イベント引数**: イベント発生元のプレイヤー・パーツ情報は、将来のマルチプレイを見越して明示的なコンテキストとして渡す。暗黙の「現在のプレイヤー」に依存しない。
5. **検証**: ID、文字列長、数値範囲、配列長、対象存在を境界で検証する。存在しない対象は安全に失敗し、警告を出す。
6. **互換性**: 既存IR命令、保存済みBlocklyワークスペース、旧eventRulesを壊さない。既存命令は必要な移行期間中維持する。
7. **制限**: ブロック数、深さ、タスク数、1フレームの処理量に上限を維持する。ゲーム内スクリプトから任意ネットワーク・DOM・ファイルアクセスは提供しない。
8. **テスト**: 各ブロックに compilerテスト、Runtimeテスト、必要に応じてengine adapterテストを追加する。

## M1の実装フェーズ

### M1-A: 既存ブロックの整合性

- ツールボックスに表示される全ブロックのコンパイル対応を棚卸しする。
- 未対応ブロックを実装するか、ツールボックスから一時的に外す。
- 未対応ブロックを黙って無視せず、コンパイルエラーとしてStudioへ返す。
- 文字列・真偽値・数値の型チェックと既定値を統一する。

### M1-B: データ・計算ブロック

- 文字列リテラル、文字列結合。
- 真偽値、論理演算、比較。
- 乱数（シード可能なRuntime内PRNGを使用）。
- リストの作成・長さ・取得・追加・置換。
- 変数の設定・取得・増減。
- 時刻・経過時間の取得。

### M1-C: パーツAPI

- 色、サイズ、位置、回転、透明度、衝突可否の取得・設定。
- パーツの検索はID/nameの曖昧な衝突を避けるAPIにする。
- 複製・削除はワールドのライフサイクル、衝突、トリガー、破棄処理への影響を調査してから実装する。M1初期には含めない。

### M1-D: プレイヤーAPI

- プレイヤー識別子を引数に取るAPIを基本にする。
- HP・生存状態・位置・移動速度・ジャンプ力の取得・設定。
- ダメージ処理はサーバー権威型マルチプレイでも利用できる境界に置く。現行シングルプレイ実装では単一プレイヤーアダプターを提供する。
- 未実装のプレイヤー機能をUI上で利用可能と誤認させない。

### M1-E: イベント・ゲームAPI

- 現行のstart/touch/leave/spawn/intervalを整理。
- player join/leave等は接続ライフサイクルが存在する段階で追加する。
- ゲーム状態とタイマーの読み取りAPIを追加。
- ラウンド管理・HUD・通知UIの完成は後続フェーズに分ける。

## 完了条件

- Blocklyツールボックスに表示される全ブロックが、定義・コンパイル・Runtime実行・テストの一貫性を持つ。
- APIが名前空間とアダプター境界で整理され、RuntimeからThree.jsやGame内部オブジェクトへ直接アクセスしない。
- 既存ワールドと保存済みBlocklyデータが引き続き動作する。
- 無効値・未知の命令・上限超過を安全に処理する。
- `npm test` と `npm run build` が成功する。
- Studio上で代表的なサンプルロジックを実際に実行確認する。

## 実装順

M1-A → M1-B → M1-C → M1-D → M1-E。各フェーズごとにテストとビルドを通し、差分を小さく保つ。


### M1-A 実装メモ（2026-11-02）

- 標準ツールボックスから未対応の `controls_whileUntil` を除外。保存済みデータに残っている場合はコンパイル時に未対応ブロックとして報告する。
- 表示対象の標準制御・計算・論理・変数ブロックをコンパイラと照合し、既存のIR命令へ変換する。
- 未対応のトップレベル／処理／値ブロック、未知の演算子、入力型の不一致、不正な数値フィールドをコンパイルエラーにする。
- 空の数値入力は数値0、空の真偽値入力はfalseとして扱う。数値フィールドは有限値を確認し、±1,000,000,000の範囲に制限する。
- Runtimeで未知の値命令・処理命令に遭遇した場合は、同じ内容の警告を一度だけ通知して安全にスキップする。数値IRの非有限値も0として扱う。
- テストには、標準ブロック群、入力型エラー、空入力の既定値、未知ブロック、数値境界、Runtime警告のケースを追加した。

※ GitHub上の変更は反映済み。テストとビルドの実行確認は、開発環境で `npm test` と `npm run build` を実行して行う。


### M1-B 実装メモ（2026-11-02）

- 文字列リテラル `rbxl_text` と文字列結合 `rbxl_text_join` を追加。文字列は最大500文字に制限する。
- 真偽値・論理演算・比較はM1-Aで整えた既存IRを継続利用する。
- `rbxl_random` を追加。Runtime内のxorshift32 PRNGを使用し、プログラムの `randomSeed`（未指定時は固定seed）で再現可能にする。整数範囲は両端を含む。
- `rbxl_list_create`、`rbxl_list_length`、`rbxl_list_get`、`rbxl_list_add`、`rbxl_list_replace` を追加。インデックスは1始まり、最大100要素。範囲外アクセスは安全な空文字または警告で処理する。
- 変数の設定・取得を数値以外にも対応させ、文字列・真偽値・リストを保持できるようにする。増減ブロックは従来どおり数値専用。
- `rbxl_elapsed_time` でRuntime開始後の経過秒数を取得できるようにする。実時間や端末時計には依存せず、ゲーム更新時間を利用する。
- 文字列長、リスト要素数、入れ子深度、数値範囲に上限を設け、変数の取得時にはコピーを返して内部配列の直接変更を防ぐ。
- テストに文字列結合、汎用変数、リスト操作、シード付き乱数、経過時間、データ上限を追加した。

※ GitHub上の変更は反映済み。テストとビルドの実行確認は、開発環境で `npm test` と `npm run build` を実行して行う。


### M1-C 実装メモ（2026-11-02）

- Blocklyにパーツ色リテラル、色の取得・設定、サイズ・位置・回転・透明度・衝突可否の設定、数値プロパティと衝突可否の取得ブロックを追加。
- コンパイラはパーツ操作を `partSet` / `partGet` のデータ専用IRに変換する。回転はXYZ順の度数、透明度は0〜1、サイズは各軸0.1〜1000、位置は各軸±100,000の範囲。
- Runtimeは `getPartProperty` / `setPartProperty` アダプターだけを利用し、Three.jsやワールド内部オブジェクトへ直接アクセスしない。
- Worldアダプターでパーツ色・サイズ・位置・回転・透明度・衝突可否を更新。衝突体とトリガー情報も可能な範囲で同期する。
- 透明度をスクリプトから変更する場合は対象パーツのみ個別メッシュへ切り替え、通常のパーツはInstancedMesh描画を維持する。
- IDを優先して対象を解決し、名前指定は一意の場合だけ許可する。同名パーツが複数ある場合は曖昧な名前指定を失敗させる。
- 複製・削除は今回も対象外。動的なパーツ生成・破棄、トリガー一覧の管理、衝突体の完全なライフサイクル管理を別途設計してから追加する。
- `test/scripting.test.mjs` にコンパイラ／Runtimeのテスト、`test/world-part-api.test.mjs` にワールドアダプターのテストを追加し、`npm test` の対象に含めた。

※ GitHub上の変更は反映済み。テストとビルドの実行確認は、開発環境で `npm test` と `npm run build` を実行して行う。


### M1-D 実装メモ（2026-11-02）

- Blocklyに独立した「プレイヤー」カテゴリを追加。プレイヤー情報取得、生存状態、HP設定、位置設定、移動速度・ジャンプ力設定、ダメージ、回復、既存のパーツへの移動とリスポーンを配置。
- すべてのプレイヤーブロックはプレイヤーIDフィールドを持ち、現行シングルプレイでは `local` を指定する。将来の複数プレイヤー対応に備えてRuntimeからIDを明示してAPIアダプターへ渡す。
- 取得プロパティはHP、最大HP、生存状態、位置XYZ、移動速度、ジャンプ力。設定プロパティはHP、位置XYZ、移動速度、ジャンプ力。
- 初期HP・最大HPは100。HPは0〜最大HP、移動速度とジャンプ力は0〜200、位置は各軸±100,000に制限。
- ダメージでHPが0になると死亡状態になり、移動・ジャンプを停止する。スクリプトの更新は継続し、リスポーン時にHPを最大値へ戻す。
- 回復は生存中のみ可能。HP設定で0より大きい値を設定すると生存状態へ戻る。
- Runtimeは `getPlayerProperty` / `setPlayerProperty` / `damagePlayer` / `healPlayer` のアダプターAPIだけを利用する。現行エンジンは `local` 以外のIDを拒否し、将来のサーバー権威型マルチプレイ用の境界を維持する。
- 既存の `rbxl_teleport` / `rbxl_respawn` は保存済みワークスペースとの互換性を維持しつつ、プレイヤーカテゴリへ移動。IDが未保存の旧ブロックは `local` として扱う。
- `test/player-api.test.mjs` にコンパイラ、Runtimeアダプター、Game側のID検証・数値制限・死亡・復活のテストを追加し、`npm test` の対象に含めた。

※ GitHub上の変更は反映済み。テストとビルドの実行確認は、開発環境で `npm test` と `npm run build` を実行して行う。
